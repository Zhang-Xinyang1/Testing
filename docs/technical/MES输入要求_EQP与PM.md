# MES 输入要求：EQP、Prober 对应关系与 PM

更新日期：2026-11-11。Probe（下文对应 proberID）与 EQP 是组装在一起的设备。以下为当前实现的字段和执行规则。其他业务表沿用现有字段。

## 1. 业务规则

1. PM 的维护对象可以是 EQPID，也可以是 proberID。通过本次生效的 EQP 数据确定对应关系，编号匹配忽略大小写、首尾空白和全半角差异。
2. **任一部件维护，整个组合设备都停止生产。**EQPID PM 和对应 proberID PM 的停机范围对称。若同一 proberID 出现在多条 CP EQP 行中，按同一关联组处理：其中任一 EQP 或该 prober 维护时，所有这些 EQPID 都停机，必须共同找到连续空档。
3. **维护任务与停机区间分别统计。**单独维护 EQP 时，Probe 连带停机，但不凭空增加一条 Probe 维护任务；反之同理。若同时提供两者的 PM，则两项维护都必须保留并执行完整时长。
4. **两条都指定 Start、区间有重叠且属于同一关联组时，只合并停机时间，不删除或替代任何一项维护任务。**停机区间取最早开始至最晚结束，不能相加时长，也不能截短任何一条。连续重叠的多条 EQP/PROBER 记录可共用一次组合停机，保留全部来源。
5. 只有 Early/Due/Over 日期窗口重叠不触发合并；只有一条填写 Start 也不触发。前一条结束等于后一条开始属于首尾相接，仍是两次。同一对象类型的记录不会单凭重叠自动去重。
6. 合并前逐条校验日期和时长。合并后的区间继续避让 WIP 等资源占用；无法满足固定时间时返回冲突。OVEN PM 保持整机全部腔体停机。
7. 此次使用的是排产周期内固定的设备关联快照，没有实现随时间换配的 prober 关系，也没有新增独立 prober 生产资源。关联发生变化时须更新 EQP 快照并重新排产。

## 2. EQP 数据字段

接口适配后的数组名为 `eqp`。Excel 对应 `EQP` 表，已有设备字段保留。

| Excel 列名 | fieldMap 映射字段 | 后端数据字段 | 必填条件 | 用途 |
|---|---|---|---|---|
| EQPID | id | id | 必填 | tester 或 OVEN 设备编号，大小写归一后唯一。 |
| TYPE | type | type | 必填 | CP 机台组；包含 OVEN 时识别为烤箱。同一 TYPE 可以重复。 |
| proberID | proberId | proberId | 现场组合设备应填写；PM 引用 prober 时必须有值 | 与本行 EQPID 组装在一起的 prober 编号。每行一个编号；多行填写同一 prober 表示同一关联组，其中任一部件 PM 都使该组全部 EQPID 停机。确实无关联时留空；旧数据未提供时只能按独立 EQPID 处理，不猜测对应关系。 |
| Status | status | status | 需要安排新增生产时必填 RUN | 其他状态不安排新增生产；状态不替代 WIP 占用。维护对象解析不因设备非 RUN 而丢弃关联。 |
| Current ProbeCard | currentCard | card | 可选 | 当前针卡类型，用于换卡计时。 |
| Current Recipe | currentRecipe | recipe | 可选 | 当前 Recipe 信息，不代表额外加工许可。 |

`proberId` 与 ProbeCard 含义不同。不要为了支持 prober PM 而增加一台虚构 CP 设备。

Excel 的 `proberID` 列可自动读取，旧配置缺少新字段映射也兼容。自定义列名需要增加 `"proberId": "实际列名"`。页面“设备与 prober 对应关系”可以查看、修改并保存该字段。

**手工 EQP 配置仍会整体覆盖 Excel EQP。**已有手工配置如果没有 proberId，不会自动从 Excel 补回；应补齐当前有效配置，或确认需要采用 Excel 后恢复参考配置。恢复操作会清除 EQP、PM、借机和 WIP 的全部手工覆盖。

## 3. PM 数据字段

接口适配后的数组名为 `pm`。Excel 默认仍使用 `PM计划` 表和原五个必填列。

| Excel 列名 | 后端／映射字段 | 必填条件 | 格式、单位及用途 |
|---|---|---|---|
| EQP ID | eqp | 必填 | **维护对象编号**。该列现在同时接受 EQPID 和 proberID，不需要将原始 prober 编号改成 tester 编号。 |
| Early Due | early | 必填 | 最早允许开始日期，建议 YYYY-MM-DD。 |
| Due Date | due | 必填 | 期望日期，必须满足 Early ≤ Due ≤ Over；当前不优化与 Due 的距离。 |
| Over Due | over | 必填 | 最迟完成日期，包含当天。每条原始计划的完整区间必须在自己的窗口内。 |
| Estimated Hours | hours | 必填 | 连续维护小时数，有限正数，最大 744，可有小数。 |
| Start | start | 可选；需要按指定时间合并时两条均必填 | 指定开始时间，例如 2026-11-10T08:00:00+08:00。预计结束由 start + hours 推导。现在 Excel、页面及后端均支持。 |
| TargetKind | targetKind | 可选；编号同时命中两类对象时必填 | `EQP` 或 `PROBER`，留空自动识别。EQP 包含 tester 和 OVEN；不要填写 OVEN、TESTER 或 COMBINED。 |

MES 只提供开始和结束时间时，适配层应计算 `hours = (结束时间 - 开始时间) / 3600秒`，同时传入 start。当前没有直接读取 PM End 列的逻辑。

未提供 Start 时，在 Early 至 Over 范围内寻找最早连续空档。**不要用 Due Date 自动拼出 Start**，否则会将可移动维护变成固定预约，也可能错误合并计划。

标准 Start、TargetKind 表头在旧 fieldMap 下也能识别。自定义表头时分别配置 `start`、`targetKind`。JSON 属性名按表中拼写，属性值中的业务编号和 TargetKind 忽略大小写。

## 4. 输入示例与结果

以下为完整排产输入中的 EQP、PM 片段，不是可单独调用的 MES 接口请求；MPS、路线、针卡、Lot 等其他输入仍需要提供。

```json
{
  "eqp": [
    {"id": "TESTER-01", "type": "K8000L", "proberId": "PROBER-01", "status": "RUN", "card": "CARD-A", "recipe": "RCP-A"}
  ],
  "pm": [
    {"eqp": "TESTER-01", "targetKind": "EQP", "early": "2026-11-10", "due": "2026-11-10", "over": "2026-11-10", "hours": 4, "start": "2026-11-10T08:00:00+08:00"},
    {"eqp": "PROBER-01", "targetKind": "PROBER", "early": "2026-11-10", "due": "2026-11-10", "over": "2026-11-10", "hours": 4, "start": "2026-11-10T10:00:00+08:00"}
  ]
}
```

以上输入保留两项维护：TESTER-01 维护 08:00–12:00，PROBER-01 维护 10:00–14:00。组合设备整体在 08:00–14:00 停机，共 6 小时；两项维护任务合计各 4 小时，不能误读为只维护了其中一个部件。

| EQPID 的指定区间 | 对应 proberID 的指定区间 | 执行结果 |
|---|---|---|
| 08:00–12:00 | 无此项维护 | 只维护 EQP，但 EQP 和 Probe 整组停机 08:00–12:00。 |
| 无此项维护 | 08:00–12:00 | 只维护 Probe，但 EQP 和 Probe 整组停机 08:00–12:00。 |
| 08:00–12:00 | 08:00–12:00 | 两者都维护；一次组合停机，占用 4 小时。 |
| 08:00–12:00 | 10:00–14:00 | 两者按各自时间维护；整组停机 08:00–14:00，占用 6 小时。 |
| 08:00–16:00 | 10:00–12:00 | 两者都维护；整组停机 08:00–16:00，占用 8 小时。 |
| 08:00–12:00 | 12:00–16:00 | 两项维护、两个首尾相接的停机事件，中间不能生产。 |
| 08:00–10:00 | 14:00–16:00 | 两项维护、两次整组停机，中间时间可用于其他合适任务。 |
| 均未指定，只给同一日期窗口和各 4 小时 | 均未指定 | 两项任务分别安排，共占用 8 小时；窗口重叠不代表已指定同时维护。 |

一台 prober 关联多台 tester 时，任一部件 PM 的整个停机区间都会阻塞所有关联 tester；共享关系必须来自真实设备快照，不能将不同实体误填为相同 proberID。

## 5. 返回字段与统计口径

`pmRecords` 每条表示一次实际停机事件；该事件内可能包含多项部件维护任务：

| 字段 | 含义 |
|---|---|
| id | 本次输入最早来源行的内部编号，例如 PM-01。 |
| eqp | 第一条来源的维护对象编号；合并维护的全部对象应查看 sourcePlans。 |
| targetKind | 实际类型：EQP、PROBER；合并结果为 COMBINED。COMBINED 仅用于输出。 |
| affectedEqps | 实际停机的 EQPID 列表。 |
| affectedProbers | 连带停机的 proberID 列表。表示停机范围，不表示自动新增这些部件的维护任务；维护任务以 sourcePlans 为准。 |
| resources | 实际阻塞资源，CP 为 EQPID，烤箱为各腔体 ID。 |
| start / end | 组合设备实际停机开始／结束，Unix 毫秒时间戳。 |
| hours | 实际连续停机小时数，合并时为区间并集长度。 |
| merged | 是否由多条原始 PM 的重叠停机区间合并；各原始任务仍完整保留。 |
| sourceIds | 所有来源行编号，例如 ["PM-01", "PM-02"]。 |
| sourcePlans | 每条原始 PM 的编号、对象、对象类型、窗口、时长及指定开始。 |

`metrics.pmInputCount` 为原始维护任务条数；为兼容现有接口，`pmCount` 保留字段名，含义为实际停机事件数；`pmMergedRows` 为输入任务数与停机事件数之差，不代表删掉了维护任务。两条重叠计划对应 2、1、1，停机时间只累计一次，两项维护均在 `sourcePlans` 保留。原始 Excel、配置和输入 pm 数组不被合并改写。

页面“PM 执行对应关系”和 PM 详情区分维护对象、连带停机对象与停机时间；PM CSV 每项原始维护任务一行，通过 `EventID` 对应实际停机事件，统计停机次数须按 `EventID` 去重。

## 6. MES 同步边界

- MES 应提供同一快照下的设备对应关系和有效 PM 记录。取消、作废、已完成且不再影响未来排产的计划，由适配层按业务口径过滤；目前没有 PM 状态自动过滤逻辑。
- 建议 MES 保留自身稳定的 `pmId`、`updatedAt` 和快照时间用于更新追踪。当前 PM-01 等是输入行编号，不是 MES 业务主键；本次未实现增量同步或按 pmId 去重。
- 未知对象、缺少 prober 对应关系、歧义编号未指定类型、无效日期、时长错误均返回错误，不猜测设备。
- 本次已实现 Excel 导入、手工配置及 `/api/schedule` 完整输入中的 prober PM 处理；Oracle/MES 自动取数连接仍需现场适配，不存在独立的 PM 拉取接口。
- 借机、WIP、禁加工仍按 EQPID 关联，本次没有将这些表的设备字段扩展为 proberID。
