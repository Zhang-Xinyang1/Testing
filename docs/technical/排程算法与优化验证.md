## LotID 重复问题的结论

上游提交 [598a080：放宽了字段逻辑](https://github.com/Zhang-Xinyang1/Testing/commit/598a080912ddd4376a4d714231691f03468996cb) 已移除 LotID 唯一性限制。`server_core.validate_schedule` 只要求 LotID 非空；`scheduler.simulate` 根据原始行号生成 `LOT-000001` 形式的唯一键，CP 任务携带 `lotKey`，前端按行键定位详情。

本次增加了实际 XLSX 的 HTTP 集成回归：上传 → Sheet/字段映射 → `/api/preview` → `/api/schedule`。文件含 72 个不同 LotID、476 行实际 Lot 明细；各行独立保留，按原 wafer 数完成 11,000 wafer。另有重复 ID 搜索的确定性和资源约束测试。原 Excel 不修改。

因此，最新源码的普通 Lot 明细导入已经支持重复 ID；未连接用户部署中的进程，不能据此确认服务器已经更新。若仍提示“LotID 不能重复”，核对部署版本、完整更新文件，运行 `python 重启服务.py` 并刷新页面。在制 WIP 现按行键定位：LotID 唯一时自动关联；同名时必须填写 `lotKey`（如 `LOT-000001`），仅排除所选行。重新导入或调整行顺序后须重新核对行键。

本次还修复了 Windows 跨盘路径问题：代码在 E 盘、配置在 C 盘时，原 `os.path.relpath` 抛错，导致导入预览/保存返回 400。现在回退为绝对路径标签。

## Platform 与机台组匹配

`Platform 必须直接匹配 EQP.TYPE：t5830;k8000L` 表示有效机台配置未匹配到一个或多个组，与 TYPE 重复无关。多个不同 EQPID 具有同一个 TYPE 是正常输入，无需删除这些设备。

现已将导入、校验、排产和诊断统一为同一格式匹配规则：清理空白、全半角和不可见字符，并将 EQP.TYPE 与各处 Platform 统一为大写；大小写不同的同型号设备共同计入容量。真实不同型号不会模糊匹配。新报错会列出缺失的组、当前读取到的 TYPE 和配置来源，也检查实际 Lot 的 Platform。

另一个已复现原因是新 Excel 的 EQP 被旧手工机台配置覆盖。检查“数据配置 → 生产配置”中的机台表和覆盖来源提示：如需保留手工计划，更新机台表；如需完整采用新 Excel 参考配置，可使用“恢复参考配置”，但该操作会清空机台、PM、借机和在制的全部手工覆盖。不会自动替用户清空。

回归覆盖重复 TYPE 正常排产、`t5830;k8000L` 大小写/全半角变化、未知型号仍拒绝、混合大小写设备合并容量、原 Excel 与手工覆盖的来源提示，以及 `/api/schedule` 的成功和失败响应。未读取现场实际 Excel，因此不能仅凭旧报错确定现场缺失的是哪一组。

## 原算法结构

```mermaid
flowchart LR
    A[Excel 映射与校验] --> B[Lot 展开与路线解析]
    B --> C[PM/借机/WIP 资源日历]
    C --> D[CP 机台组预分配]
    D --> E[事件堆推进时间]
    E --> F[CP 公平序派工与 BAKE 合批]
    F --> E
    F --> G[完整路线完成后统计 wafer]
    G --> H[比较 0/4/8h 组批窗口]
```

主要代码在 `backend/scheduler.py`：`_assign_preferred_types` 根据组内剩余月机时分配 Lot；`_fair` 使用“该 Lot 前累计 wafer / PPN MPS − 0.20 × 产品归一化 CP 工作量”排序；`simulate` 通过最小堆推进释放、CP 完成、QTIME 完成和 BAKE 放行事件。

资源可用时，CP 按机台顺序从每个产品/工序队首选 Lot；BAKE 从同 Recipe 队列取最多 4 Lot，不满批则按指定窗口等待。PM 和借机在派工前选定时段，生产中不抢占。原方案已有三种 BAKE 等待窗口的枚举，但每个窗口内仍是一次贪心构造。

不足包括：一次决策不回看完整结果；静态公平序不能反映后续 BAKE/CP 的时间压力；整条路线固定一个组可能浪费其他组能力，甚至错误拒绝“每道工序分别有可用组，但没有一个组支持整条路线”的 Lot；只看队首可能遗漏后面的可加工 Lot。

## 本次实现：多起点 + 完整仿真 + 局部搜索

`backend/optimizer.py` 负责搜索，原事件引擎负责解码和保证约束。

1. 先运行原贪心方案，保留其最优窗口结果作为基线。
2. 比较三种确定性派工配置：均衡、长剩余路线优先、短剩余路线优先；各自比较相同的 BAKE 窗口。候选按工序选择兼容机台，不再将整个 Lot 固定到一组，也会检查队列后面的 Lot。
3. 用路线后缀时间估算最早可能完工时刻：CP 按实际 wafer，加 BAKE 放行前 26h 和 QTIME；不含排队与未来换卡，因此是乐观下界。已经不可能在截止前完成的 Lot 排在仍有希望的 Lot 后面，但仍生成其后续排程。
4. 对当前最好结果中的低达成率产品调高派工优先级，对临近截止后完成的 Lot 做优先级插入调整。每次重新执行完整仿真，接受综合目标严格更好的候选。默认额外评估最多 8 个邻域候选，重复配置跳过。
5. 返回最优已发现方案，同时报告基线、候选结果和选中策略。相同输入/选项的排程可复现，运行时间和记录时间除外。

每个候选继续遵守 RUN/Platform/Recipe/禁加工、资源不重叠、路线先后、5 分钟换卡、BAKE 最多 4 Lot、26h 放行/28h 占腔、PM、借机和 WIP 等原约束。局部搜索不直接修改任务时间。日历空档按当前机台和工时缓存；机台当前处于占用区间时跳过无意义的队列扫描。

## 目标函数与边界

对每个正需求 PPN，计算 `r[p] = 月内完整路线完成 wafer / MPS wafer`，评分时截到 1。将这些比率升序排列，按字典序最大化：先改善最差产品，再改善次差产品，依次类推。比率比较保留 12 位小数。

整个比率向量相同时，依次比较：更多月内 wafer、更少不可排 Lot、更短全部 Lot 的最终完工跨度、更少换卡时间。这与仅优化最低值不同：最低值被不可达产品卡在 0 时，仍能改善其他产品。

基线始终作为候选，故上述综合目标不会变差；并不保证每个 PPN 的达成率或总 wafer 分别单调增长。它是有界启发式搜索，没有最优性证明，也没有下界差距证明。默认 3 个窗口 ×（1 个基线 + 3 个新策略）+ 最多 8 个邻域候选，即最多 20 次完整仿真；耗时约随候选数增长。PM/借机时段本次仍先固定，未纳入局部搜索；未实现滚动重排或人工锁定任务。

这类问题包含可选机台、工序前后约束、批加工和日历。若后续需要最优性界限，可继续建设 CP-SAT 模型，用可选区间与 NoOverlap 表达选机/互斥，再专门建模同 Recipe 合批、换卡和产品达成率；不能直接用普通最短工期 Job Shop 示例替代现有业务约束。建模基础可参考 [Google OR-Tools 官方 Job Shop 文档](https://developers.google.com/optimization/scheduling/job_shop)。本次保持运行时零第三方依赖。

## 稳定性排查与验证

本次同时修复以下问题：

- Excel 读取保留空行对应的物理表头位置，支持 1904 日期系统与秒精度，避免带单位数值被误识别为日期；重复表头、歧义映射、明确配置但缺失的 Sheet、空的实际 Lot 表会明确报错。
- 统一日期、产品、行键和 WIP 解析；拒绝非法日期、非有限工时、无效资源引用、重复或重叠周目标。校验不修改调用方输入。
- 固定 PM/借机优先预留，保留原记录 ID；WIP 释放后按实际针卡计算换卡时间；修复跨平台完成量与月末边界统计。
- 前端忽略过期请求结果，诊断使用对应请求快照；保存配置时复用完全相同的已验证预览，避免重复计算，输入或选项改变则重新排程。

验证：87 项 Python 测试、5 项 Node 前端测试通过；完整算例的 8 组独立业务约束检查全部通过，11,000 wafer / 476 Lot 完成；部署检查和字段检查通过。测试命令另包括 `node --test tests/frontend_state.test.js`、`python deploy.py check`、`python tools/check_fields.py`。
